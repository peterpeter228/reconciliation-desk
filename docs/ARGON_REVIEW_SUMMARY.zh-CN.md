# Argon 审查后的核实与修复结果

2026-10-21。目标项目：Reconciliation Desk。

## 结论

本轮真实调用成功，HTTP 200，耗时约 103 秒。不是只做连接测试：已发送 45 个核心源码、测试和规格文件，收到完整静态审查。随后逐条复现、区分误报与限制，并实际修复成立的问题。

修复后，329 项 TypeScript 测试全部通过，类型检查、格式检查、构建、产物检查通过；原始 Python 参考组件另有 33 项测试通过。测试数不能相加当作独立覆盖率，也不构成财务或安全认证。

## 主要修复

1. 待结算、未知或仍冻结的结算记录，不能再凭预计费用和净额被当作已实现的手续费或结算证明。
2. 重导总账验证必须有同一公司、同一 QBO/QBD 产品下的可靠交易 ID，并检查该交易全部已提供分录行。相同单据号不能拼接两笔交易，也不能漏掉单据号为空的额外行。旧报表仍可读取，但缺 ID 时保持未核实。
3. 退款诊断不再复用一份模糊确认函覆盖多笔退款；确认状态要求逐笔退款证据。批次匹配不能漏掉同批次的退款。
4. “Total Comfort Heating & Air”等客户名开头的有效明细，不再被误当汇总行丢弃；格式错误的业务行必须报错，不能悄悄排除。
5. XLSX 的关系和内容类型元数据增加严格校验，保留正常命名空间；修复的是限定格式导入保护缺口，没有证据表明曾发生外部请求、数据泄漏或代码执行。
6. 补强直接调用验证函数时的运行时校验：非 USD、伪布尔值、无效金额关系、错误来源、错误日期范围或未解决字段，不能被标为已入账。
7. 费用规则升级为 fee-only-1.1，旧规则下的批准即使哈希自洽，也需要重新生成和复核。

## 没有照单采纳的建议

- Argon 将“拆分入账被拒绝”标为 P0。实际是已明确不支持、并且不分配金额的安全限制，不是错误接受资金。没有按相同存款号简单合并银行流水。
- 一项所谓清算金额绕过，原代码已经通过金额方程阻止。另一个复合分录变体归为窄模板范围加固，不冒称已证实会生成错误手续费。
- 脱敏预览没有复现原始数据泄漏；仅改进数字类型提示，避免把邮编等纯整数误当金额。
- 模型没有实际运行代码。其“已确认”“不存在漏洞”等措辞不能代替我们的测试，更不能被当作安全保证。

## 性能与范围

修复后在 Node 中，对每种场景各运行 3 次预热和 20 次计时：3,000 行身份明确场景 p95 为 350.88ms；含歧义与搜索上限的混合场景为 441.29ms。混合场景保留 90 个未完成搜索范围，没有为了达标强行确认。该结果不包含解析、浏览器或界面耗时，不是任意文件的性能保证。

调用请求型号为 gemini-4-argon-high，供应商返回的 modelVersion 为 gemini-4-argon；真实上游档位无法独立证明。返回使用量为 107,299 tokens，实际金额未知。第一次网络错误的记录保留；第二次为用户明确允许后的单次重试。没有再次把修复后的代码交给 Argon 复审。

## 仍未完成

- 真实浏览器核心桌面流程已在后续通过限定范围检查；移动端、打印/PDF、运行时网络和下载清单仍未全部验收。
- 后续已在 QBO 官方公开样例公司成功导入并核对一笔纯合成日记账；原生 CSV/XLSX 报表回导失败，完整往返和 QBD 导入仍未通过。
- 拆分结算等明确列出的未支持场景。
- 后续已建立仅用户可见的 QA 测试站，并在授权登录后完成核心桌面流程检查，不能据此称为可上线产品。没有连接真实财务账户、对真实账簿写账、收费或公开发布；后续仅在 QBO 官方公开样例公司执行了单笔合成导入。
